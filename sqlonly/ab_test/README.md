# ab_test — 개입 효과 검증 설계

## 이 폴더가 따로 있는 이유

`sql/` 은 **지금 실제로 돌아가는** 쿼리이고,
`ab_test/` 는 **아직 데이터가 없어 돌아가지 않는** 설계입니다.

가르는 기준은 하나입니다.

> **지금 실행하면 결과가 나오는가?**

| | 폴더 | 실행하면 |
| --- | --- | --- |
| 예측 결과 조회·집계 | `sql/` | 결과가 나옴 |
| 개입 배정·효과 측정 | `ab_test/` | **0행** (데이터가 없음) |

섞어 두면 팀원이 돌려보고 "왜 아무것도 안 나오지?" 하고 헤맵니다.

---

## 왜 A/B 테스트가 필요한가

우리가 찾은 것은 **상관관계**입니다.

```
자기소개 0칸  →  이탈률 58.9%
자기소개 1칸  →  이탈률 44.1%
```

여기서 **"쓰게 만들면 안 떠난다"는 결론은 나오지 않습니다.**
원래 앱에 관심 있는 사람이 글도 쓰는 것일 수 있기 때문입니다.

인과를 확인하려면 **같은 조건의 사람을 반으로 나눠서 한쪽에만 개입**해야 합니다.
그게 A/B 테스트입니다.

## 실험 설계 요약

```
1. 대상 선정      High 위험군 + 자기소개 7칸 이하
2. 무작위 배정     random() 으로 treatment / control 반반
3. 공정성 확인     두 집단 평균 위험도가 비슷한가
4. 개입           treatment 에만 넛지 푸시 발송
5. 30일 대기
6. 결과 비교      잔존율 · 프로필 수정률
```

### 3번을 빼먹지 마세요

배정 직후 두 집단의 평균 위험도를 비교합니다.
한쪽이 눈에 띄게 높으면 **재배정**합니다.

이걸 안 하면 나중에 차이가 나도 개입 덕분인지
원래 다른 사람들이었는지 구분할 수 없습니다.

### control 집단에는 아무것도 보내지 마세요

한 명이라도 보내면 실험이 무효가 됩니다.
`01_design.sql` 4단계 쿼리에 `AND a.arm = 'treatment'` 조건이 들어 있는 이유입니다.

## 젤리 보상 — 왜 "길이"가 아니라 "질"인가

글자 수로 젤리를 주면 **의미 없는 장문**이 늘어납니다.
그래서 다른 사용자가 남긴 평가를 기준으로 지급합니다.

```
프로필이 알차요 · 대화를 시작하기 쉬워요 · 가치관이 잘 드러나요
```

### 칭찬 수가 아니라 칭찬률

```
칭찬률 = 칭찬 수 ÷ 프로필 노출 수
```

노출이 많으면 칭찬도 자연히 많아집니다.
분모로 나눠야 신규 사용자와 기존 사용자를 공정하게 비교할 수 있습니다.

### 어뷰징 대비

젤리처럼 **실제 가치가 있는 보상**에는 반드시 어뷰징이 따라옵니다.
`02_quality_reward.sql` 에 두 가지 탐지 쿼리를 넣어 뒀습니다.

- 서로 칭찬 품앗이 (self-join으로 상호 칭찬 탐지)
- 한 사람이 비정상적으로 많이 뿌리는 경우

> 대안: 젤리 대신 **노출 부스트**로 주면 원가가 0원이라
> 어뷰징을 당해도 회사가 잃는 것이 없습니다. 검토해 볼 만합니다.
